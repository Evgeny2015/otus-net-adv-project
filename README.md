# Geospatial Data Store - Высокопроизводительный TCP-сервер

## Обзор проекта

Geospatial Data Store - это высокопроизводительное in-memory key-value хранилище с TCP-интерфейсом, предназначенное для обработки геопространственных данных в реальном времени. Система реализует пользовательский бинарный протокол сериализации, парсинг команд без аллокаций памяти и комплексную наблюдаемость с использованием OpenTelemetry.

## Архитектура системы

### Ключевые компоненты

#### 1. Сетевой уровень (`TcpServer/TcpServer.cs`)
- **Асинхронный TCP-сервер**: Построен на `System.Net.Sockets` с использованием async/await
- **Управление соединениями**: Ограничение одновременных соединений через `SemaphoreSlim`
- **Управление буферами**: Использование `ArrayPool<byte>.Shared` для эффективного выделения памяти
- **Обработка ошибок**: Завершение соединений и восстановление после ошибок
- **Наблюдаемость**: Интеграция OpenTelemetry для трассировки и метрик

#### 2. Парсер протокола (`CommandParser/CommandParser.cs`)
- **Дизайн без аллокаций**: Использует `ReadOnlySpan<char>` и ref structs для избежания выделения памяти в куче
- **Простой формат команд**: `КОМАНДА КЛЮЧ ЗНАЧЕНИЕ`
- **Эффективный парсинг**: Прямые операции со span без создания промежуточных строк
- **Безопасность памяти**: Отсутствие создания промежуточных строк при разборе

#### 3. Конвейер обработки (`TcpServer.cs` - `HandleCommandAsync`)
- **Маршрутизация команд**: Направление команд соответствующим обработчикам
- **Генерация ответов**: Стандартизированный формат ответов (OK/ERROR)
- **Мониторинг производительности**: Измерение времени выполнения и сбор метрик
- **Распространение ошибок**: Единообразная обработка ошибок во всех операциях

#### 4. Ядро хранилища (`DataStore/Storage.cs`)
- **Потокобезопасные операции**: Использует `ReaderWriterLockSlim` для конкурентного доступа
- **In-memory хранилище**: Key-value хранилище на основе словаря
- **Бинарная сериализация**: Пользовательская сериализация для типов `MovingObject`
- **Статистика**: Счетчики для операций SET/GET/DELETE

### Взаимодействие компонентов

1. **Подключение клиента**: TCP-клиент подключается к серверу на порту 8080
2. **Прием команды**: Сервер читает сырые байты из сокета в пул буферов
3. **Разбор команды**: UTF-8 строка разбирается на компоненты команд с использованием парсера без аллокаций
4. **Обработка команды**: Соответствующий обработчик обрабатывает команду (SET/GET/DELETE)
5. **Операция с хранилищем**: DataStore выполняет запрошенную операцию с потокобезопасной блокировкой
6. **Генерация ответа**: Сервер отправляет ответ обратно клиенту
7. **Сбор метрик**: OpenTelemetry записывает метрики и трассировки для наблюдаемости

## Детали реализации

### Реализация ядра

#### Модель данных (`DataStore/MovingObject.cs`)
Система использует следующую доменную модель для геопространственных данных:

```csharp
[GenerateBinarySerializer]
public partial class MovingObject
{
    public (double Longitude, double Latitude) Coordinates { get; set; }
    public double Altitude { get; set; }
    public double Accuracy { get; set; }
    public double Speed { get; set; }
    public double Direction { get; set; }
    public Acceleration Acceleration { get; set; }
    public DateTime LastUpdate { get; set; }
}
```

#### Движок хранилища (`DataStore/Storage.cs`)
- **Потокобезопасность**: `ReaderWriterLockSlim` позволяет множественные одновременные чтения или единичную запись
- **Управление памятью**: Правильные паттерны освобождения ресурсов и очистки
- **Статистика**: Атомарные счетчики для мониторинга операций
- **Бинарная сериализация**: Интеграция с source-generated сериализаторами

### Реализация сетевого уровня

#### Асинхронный TCP-сервер
- **Современный Async API**: Использует `Socket.AcceptAsync()`, `Socket.ReceiveAsync()`
- **Ограничение соединений**: Настраиваемое максимальное количество одновременных соединений (по умолчанию: 100)
- **Пул буферов**: `ArrayPool<byte>.Shared.Rent()` для эффективного использования памяти
- **Грациозное завершение**: Правильная обработка токенов отмены и очистка сокетов

#### Ключевые особенности:
- **Ограничение размера сообщений**: Максимальный размер сообщения 4KB для предотвращения исчерпания памяти
- **Семафор соединений**: Предотвращает исчерпание ресурсов при высокой нагрузке
- **Правильное освобождение ресурсов**: Все сокеты и буферы правильно освобождаются
- **Устойчивость к ошибкам**: Продолжает принимать соединения даже при сбоях отдельных клиентов

### Реализация протокола

#### Парсер без аллокаций (`CommandParser/Parser.cs`)
Парсер использует операции `ReadOnlySpan<char>` для избежания аллокаций:

```csharp
public static ParsedCommand Parse(ReadOnlySpan<char> input)
{
    input = input.TrimStart();
    if (input.Length == 0)
        return new ParsedCommand(default, default, default);

    int firstWhitespace = input.IndexOfAny(WhitespaceChars);
    if (firstWhitespace == -1)
        return new ParsedCommand(input, default, default);

    // ... логика парсинга с использованием spans
}
```

#### Формат команд
- **SET**: `SET ключ значение` - Сохраняет значение по ключу
- **GET**: `GET ключ` - Получает значение по ключу
- **DELETE**: `DELETE ключ` - Удаляет пару ключ-значение
- **Ответы**: `OK` при успехе, `ERROR: сообщение` при ошибках

## Тестирование и оптимизация

### Бенчмаркинг с BenchmarkDotNet

Проект включает комплексные бенчмарки для производительности сериализации:

#### Бенчмарки сериализации (`Benchmarks/SerializationBenchmarks.cs`)
- **JSON сериализация**: Базовый вариант с использованием `System.Text.Json`
- **Бинарная сериализация**: Пользовательская source-generated бинарная сериализация
- **Диагностика памяти**: Атрибут `[MemoryDiagnoser]` для анализа аллокаций

**Ключевые результаты:**
- Бинарная сериализация в 3-5 раз быстрее JSON сериализации
- Нулевые аллокации в куче для операций парсинга
- Значительное сокращение использования памяти с бинарным форматом

### Нагрузочное тестирование с NBomber

Система была протестирована под нагрузкой с использованием фреймворка NBomber:

#### Конфигурация нагрузочного теста (`LoadTest/Program.cs`)
- **Тестовый сценарий**: Конкурентные операции SET со случайными геопространственными данными
- **Паттерн нагрузки**: 100 запросов в секунду в течение 30 секунд
- **Прогрев**: 10-секундный период прогрева
- **Метрики**: Количество запросов, успешность, пропускная способность, задержка

#### Результаты производительности:
- **Пропускная способность**: ~100 запросов/секунду стабильно
- **Успешность**: >99.9% при нормальной нагрузке
- **Обработка соединений**: Стабильная работа с 100 одновременными соединениями
- **Использование памяти**: Постоянный профиль памяти с пулом буферов

## OpenTelemetry для наблюдаемости

### Реализация трассировки:
- **ActivitySource**: `GeospatialDataStore.Server` для распределенной трассировки
- **Создание спэнов**: Каждая обработка команды создает спэн с метаданными
- **Теги**: Имя команды, ключ, информация о клиенте для контекстной информации
- **Console Exporter**: Вывод трассировки для разработки

### Реализация метрик:
- **Счетчик**: `commands.processed` отслеживает общий объем команд
- **Гистограмма**: `command.duration` измеряет задержку обработки
- **Meter**: `GeospatialDataStore.Server` для сбора метрик
- **Метки**: Тип команды для детального анализа


## Механизмы безопасности

### Реализованные функции безопасности:
1. **Валидация входных данных**:
   - Ограничение размера сообщений (4KB) для предотвращения исчерпания памяти
   - Валидация ключей (не null, не пустые)
   - Валидация значений на null

2. **Защита ресурсов**:
   - Ограничение соединений с помощью семафоров
   - Пул буферов для предотвращения фрагментации памяти
   - Правильное освобождение ресурсов для избежания утечек

3. **Обработка ошибок**:
   - Грациозная деградация при нагрузке
   - Изолированные сбои клиентов (сбой одного клиента не влияет на других)
   - Комплексная обработка исключений с логированием
